## Open

### Docker's default address pools are exhausted: the next new compose project fails to start — OPEN, found 2026-10-11
- **Symptom:** `docker compose up -d` for a new service fails before creating anything: `failed to create network <project>_default: ... all predefined address pools have been fully subnetted`. Hit while deploying Komga.
- **Cause:** every compose project gets its own bridge network, and Docker's default `default-address-pools` hand out about 31 of them. This stack has **30 in use** (checked: none have zero containers apart from the built-in `bridge`), so there's nothing stale to prune.
- **Update 2026-10-11:** removing YACReader also removed `yacreader_default`, so **one** slot is free: the next new compose project will start, and the one after that will fail.
- **Workaround in place:** `komga/compose.yml` uses `network_mode: bridge` (Docker's built-in bridge). Fine for a container that talks to nothing else; it loses compose's per-project DNS.
- **Proper fix (Kody's call: it restarts every container):** give the daemon smaller per-network subnets, e.g. OrbStack → Settings → Docker engine config `"default-address-pools": [{"base": "10.200.0.0/16", "size": 24}]` (256 networks), then restart OrbStack. Existing networks keep their subnets until recreated. Pick a `base` that doesn't overlap the LAN (`192.168.178.0/24`) or Tailscale (`100.64.0.0/10`).

### Internal `*.kodyparton.com` names don't resolve on Kody's devices (except `home`): three stacked causes — OPEN, found 2026-10-11
- **Symptom:** `comics.kodyparton.com` "doesn't load" in Safari on Kody's iPhone/iPad/Mac. **No request ever reaches NPM, and AdGuard's query log never sees the name.** It applies to every internal name (`sonarr`, `audiobooks`, `photos`, …). `home.kodyparton.com` still works, which makes it look app-specific when it isn't: `home` is the only name with a **public** Cloudflare record (`192.168.178.69`); every other name exists only as an AdGuard rewrite.
- **Cause 1, Tailscale DNS:** with Tailscale on, `CorpDNS: true` + MagicDNS but **no nameservers configured in the tailnet**, so it falls back to the OS's DNS (cause 2). **Fix (Kody, Tailscale admin console):** DNS → Nameservers → Add nameserver → Custom `192.168.178.69` → **Restrict to domain** `kodyparton.com` (split DNS). That works on the home network; away from home, the Mac Mini also has to advertise the LAN (`tailscale set --advertise-routes=192.168.178.0/24`, then approve it in the console).
- **Cause 2, devices fall back to Ziggo DNS:** the router's DHCP hands out Ziggo's resolvers (`213.46.228.196`, `62.179.104.196`, two IPv6), which have no record for the internal names and **drop answers pointing at private IPs**, so even `home` fails through them. On the Mac Mini, the 2026-08-29 manual DNS on **Ethernet** (`192.168.178.69 1.1.1.1`, see `containers/adguard.md`) **has been wiped** (`networksetup -getdnsservers Ethernet` → none). Wi‑Fi still has it, **in the wrong order** (`1.1.1.1 192.168.178.69`): 1.1.1.1 answers NXDOMAIN first. **Fix (Kody — system network setting):** `sudo networksetup -setdnsservers Ethernet 192.168.178.69 1.1.1.1`. On iPhone/iPad: Settings → Wi‑Fi → ⓘ → Configure DNS → Manual → `192.168.178.69`.
- **Cause 3, iCloud Private Relay bypasses AdGuard even on devices that use it:** with Private Relay on, **Safari resolves names through Apple's relay**, not the local DNS server. `home` resolves there (public record) and Safari connects straight to the private IP; `comics` has no public record, so it fails without AdGuard ever being asked. Evidence: Apple devices *do* query AdGuard (278 Apple/iCloud lookups in an hour), including `mask.icloud.com`/`mask.apple-dns.net` (the Private Relay probe) at 19:19:52, while Kody was retrying comics, with no `comics` lookup alongside. AdGuard currently lets the probe through (`mask.icloud.com` resolves; no custom rules). **Fix, per device:** Settings → Wi‑Fi → ⓘ (home network) → turn off **iCloud Private Relay** for that network. **Fix, network-wide (pending Kody's decision, since it changes privacy for the whole household):** AdGuard custom rules `||mask.icloud.com^` and `||mask-h2.icloud.com^`. Apple documents this NXDOMAIN signal; devices using AdGuard then turn Private Relay off *for this network only* (with a notice) and resolve locally. Pi-hole does this by default.
- **Diagnostic trap:** on macOS, `dig` **bypasses the system resolver** (it reads `/etc/resolv.conf` only), so it can disagree with what Safari sees. Use `dscacheutil -q host -a name comics.kodyparton.com`, which goes through mDNSResponder like Safari does.
- **Rejected:** a public Cloudflare record per service. It would expose every internal hostname in public DNS, and Ziggo's resolvers would drop the private-IP answers anyway.

### ~~The NAS delivers ~0.25–3 MB/s~~ — **FULLY RESOLVED 2026-09-01. Two stacked physical faults: a bad switch port AND a bad cable.**

The single most useful lesson in this file: **this was diagnosed entirely from wire measurements, and every software-side theory along the way was wrong.** The NAS's own admin UI reported "healthy" throughout, a reboot made it measurably *worse*, and time was spent on Plex's storage tier, its Butler tasks, and a non-existent hardware-transcoding fault before the network was measured properly. Measure the wire first.

| Stage | Latency to NAS | Sustained throughput |
|---|---|---|
| Original (bad port + bad cable) | 8.9–16.8 ms, 2.4 ms jitter | **0.245–3.1 MB/s**, varying 12x between runs |
| After switch-port swap | 0.674 ms | **11.7 MB/s**, stable ±0.1 |
| After cable swap | **0.702 ms** | **104–116 MB/s** |

- **Two independent faults, and the second was masked by the first.** The bad port produced high latency and wildly erratic throughput. Fixing it revealed a hard, *flat* 11.7 MB/s ceiling — and that flatness was the tell: a device under strain varies between runs, a link at its rate limit does not. 11.7 MB/s ≈ 94 Mbps ≈ 100BASE-TX minus framing. **A cable with a damaged pair negotiates 100 Mbit instead of failing** (gigabit needs all four pairs, 100M needs two), which is why nothing ever reported an error.
- **Final state verified across both clients and both shares:** Docker native CIFS 116 MB/s (`tv-4k`) and 115 MB/s (`downloads`); macOS smbfs — the path Plex actually uses — 104 MB/s. All on 500MB/200MB sustained reads. Full gigabit.
- **Measurement caveat worth keeping:** an immediate re-read of the same file reported 6.4 GB/s. That is the page cache, not the network. Use a fresh file, or discard the first repeat.
- **Headroom now:** a 1080p stream needs ~1.32 MB/s (~85x headroom); 4K remuxes at 60–100 Mbps need 7.5–12.5 MB/s (~10x headroom). Both comfortable.
- **All 36 containers survived both link drops** with zero mount errors and no shadowed host mount — the first real-world tests of the create-time CIFS failure mode since it was documented. Nothing needed healing either time.

### (superseded) Partial fix — switch port only
- **Fix:** Kody swapped the NAS's switch port on 2026-09-01. Immediate, dramatic improvement:

  | Metric | Before | After port swap |
  |---|---|---|
  | Latency to NAS | 8.9 ms (avg), 2.4 ms jitter | **0.674 ms, 0.126 ms jitter** |
  | Latency to gateway (control) | 0.66 ms | 0.967 ms |
  | Throughput | 0.245–3.1 MB/s, wildly variable | **11.7 MB/s, stable** |

  The NAS is now *faster to respond than the gateway*. This confirms the marginal-link diagnosis: high latency + zero packet loss + no packet-size dependence really was a bad physical port, not a sick NAS. Its admin UI reported "healthy" throughout, and a reboot made things worse — neither was a useful signal. **Trust the wire measurements over the appliance's own health summary.**
- **All 36 containers survived the link drop** with zero mount errors, and the host `/Volumes/media` mount was not shadowed. The port swap was the first real-world test of the CIFS-at-create-time failure mode since it was documented, and nothing needed healing.
- **Still open, and it is a different problem:** throughput now sits at **11.7 / 11.8 MB/s across repeated runs — within 0.1 MB/s of each other.** That consistency is a hard link-rate ceiling, not a device bottleneck (contrast the pre-fix numbers, which swung 12x between runs). 11.7 MB/s ≈ 94 Mbps ≈ **100BASE-TX minus framing overhead**. The Mac's own `en0` is still `1000baseT <full-duplex>`, so the limitation is on the NAS's side of the wire: either the new switch port is a 100M port, or the cable cannot carry gigabit. **A cable with one damaged pair negotiates 100 Mbit rather than failing** — gigabit needs all four pairs, 100M needs two — which would also explain the original fault on the old port. Worth trying a known-good Cat5e/6 cable and a known-gigabit port, and checking the negotiated speed in the UNAS UI.
- **Practical impact of the residual limit:** a 1080p stream needs ~1.32 MB/s, so there is now ~9x headroom and ordinary streaming should be fine. But 4K remuxes commonly run 60–100 Mbps (7.5–12.5 MB/s), which would saturate a 100M link outright — expect the `tv-4k` / `movies-4k` libraries to still struggle until this is gigabit.

### (original diagnosis) The NAS delivers ~0.25–3 MB/s on a healthy gigabit link — this was the real cause of the Plex streaming problems
- **Found:** 2026-08-31, chasing "Plex is still having considerable issues trying to stream."
- **What:** sustained read throughput from the UNAS Pro (`192.168.178.38`) is between **245 kB/s and 3.1 MB/s**, wildly variable. A 1080p stream at 10,556 kbps needs ~1.32 MB/s sustained, so the NAS frequently cannot feed even *one* stream. Plex's client was caught live in `state=buffering` with playback progress frozen at the same millisecond across 40+ seconds of timeline reports.
- **Measurements** (all against the same NAS, various paths):

  | Path | Share | Result |
  |---|---|---|
  | macOS smbfs | `media` | 1.66 MB/s |
  | Docker native CIFS | `tv-4k` | 2.3 MB/s |
  | Docker native CIFS | `downloads` | 2.0 MB/s |
  | Docker native CIFS (after NAS reboot) | `tv-4k` | **669 kB/s** |
  | macOS smbfs (stream-copy 14.9MB) | `tv-4k` | **245 kB/s** |

- **Ruled out, each by direct measurement rather than reasoning:**
  - **Not the mount type.** macOS smbfs and Docker native CIFS are *equally* slow. This kills the standing assumption that the host-passthrough mount is the fragile part — the "proven reliable" CIFS path is just as bad.
  - **Not one share or one file** — `media`, `tv-4k` and `downloads` all measure the same.
  - **Not the link.** `en0` is `1000baseT <full-duplex>`, **0 errors, 0 collisions** across 492M packets.
  - **Not qBittorrent contention** — measured at 0 active torrents, 0 B/s up and down.
  - **Not packet loss** — 0% over 20 packets at 1400 bytes.
  - **Not SMB encryption** — negotiated SMB 3.1.1 with `SMB_CURR_ENCRYPT_ALGORITHM = OFF`.
  - **Not a bandwidth-limited medium** (powerline/wifi bridge): latency does *not* rise with packet size — it is 14.5ms at 64 bytes and 10.0ms at 1400 bytes. A constrained link shows the opposite.
  - **Not Plex.** See the hardware-transcode correction below; Plex was not even in the top 12 CPU consumers.
- **What the evidence does point at:** the NAS's own responsiveness. Latency to it is **14.9ms avg with 2.9ms jitter**, against **0.66–1.17ms to the gateway on the same LAN** — 13-26x worse, with no loss and no size dependence. Even a *cached* re-read of the same block only reached 3.1 MB/s, so the ceiling is not the disks alone.
- **A reboot made it worse, not better.** Kody rebooted the NAS after its UI reported everything healthy. Post-reboot latency roughly doubled (8.7ms → 16.8ms) and throughput dropped to 669 kB/s.
- **Next steps, and they are on the NAS/physical side, not this Mac:** check the **negotiated NIC speed and duplex on the NAS itself** (a summary "healthy" does not show this); check per-drive SMART and any rebuild/scrub in progress (a drive doing internal retries reads as healthy while performing terribly); check NAS CPU/memory load; and **swap the cable and switch port** — high latency with zero loss and no size dependence is a classic marginal-link signature.

### Plex load times vary and sometimes hang entirely — mitigated 2026-08-31, one fix still needs Kody
- **Found:** 2026-08-31, reported by the user as "load times seem to vary and sometimes hang entirely."
- **The setup that causes it:** Plex is the native macOS app, and it is now the **only** consumer left on the two storage paths this repo already knows are fragile. Its media comes over the macOS-host smbfs mount `/Volumes/media` — the exact passthrough all 9 containers were migrated *off* on 2026-08-29 — and its entire data directory, including the live SQLite library DB, is a symlink to `/Volumes/FastSSD/PlexData` on a **detachable USB SSD**. Both were known-risky in isolation; nobody had connected them to Plex's user-visible symptoms.
- **The single most likely cause, and it is still open:** `pmset -g` reports **`disksleep 10`**. Disks spin down after 10 minutes idle, and Plex's library DB — hit on every UI action — plus (until today) its transcode scratch both live on the drive that sleeps. The first action after any quiet period pays a drive-wake stall. This matches "sometimes fast, sometimes hangs" better than anything else found. **Fix needs an interactive sudo and has not been applied:** `sudo pmset -a disksleep 0`.
- **Applied 2026-08-31** (via `http://127.0.0.1:32400/:/prefs`, each change re-read back from the API afterward rather than trusted on HTTP 200):
  - `TranscoderTempDirectory` → `/Volumes/FastSSD/PlexTranscode`. It was **unset**, so transcode scratch defaulted *inside* the Plex data directory — i.e. onto the sleeping USB drive, during 4K transcodes.
  - `ScannerLowPriority` → `1`, `ButlerTaskDeepMediaAnalysis` → `0`. Extensive nightly media analysis re-reads the whole library across the SMB mount; this is the classic cause of periodic multi-minute freezes.
  - `ScheduledLibraryUpdateInterval` pinned to `3600`.
  - Already correct, left alone: `GenerateBIFBehavior=never`, Butler window 02:00–05:00.
- **Correction worth recording, because it nearly became a false finding:** `Preferences.xml` on disk contains `TranscoderTempDirectory="/transcode"` — the `linuxserver/plex` Docker convention, pointing at a path that cannot exist on macOS's read-only root. This looked like a smoking gun. It was not: the **running** server reported that value as empty, having rejected it and fallen back to the default. The on-disk file and the running server also disagreed about the scan interval (900 vs 3600). **`Preferences.xml` is not a reliable read of live Plex state — query `/:/prefs`.**
- **CORRECTION 2026-08-31 (same day):** an earlier version of this entry claimed hardware transcoding "never engages", citing `TPU: hardware transcoding: final decoder: , final encoder: ` (both empty) plus 42 `MDE: unable to find a working transcode profile for video stream` warnings. **That conclusion was wrong.** Those lines appear during *audio-only* jobs (`videoDecision="ignore"`, audio transcoded to FLAC) where no video encode is requested at all — an empty video decoder/encoder is the correct, expected output there, not a fault. Tested properly instead of inferring from logs: `Plex Transcoder -hwaccels` lists `videotoolbox`, `-encoders` lists `h264_videotoolbox` and `hevc_videotoolbox`, and a real encode of 10 seconds of 1080p **from local disk completed in 1 second (10x realtime)**. Hardware transcoding on this M1 is fully functional. The lesson: an unfamiliar log line is not evidence of a fault until the capability is tested directly.
- **Butler analysis tasks were a real but secondary load, and the controls are not where they look.** The `/butler` endpoint names tasks like `ButlerTaskGenerateIntroMarkers`, but `PUT /:/prefs` rejects those names with HTTP 400 — the actual prefs are `*Behavior` enums (`GenerateIntroMarkerBehavior` etc.) taking `asap`/`scheduled`/`never`. Three were set to **`asap`**, which **bypasses the 02:00–05:00 Butler window entirely** — that is why marker generation was caught grinding through Game of Thrones S8 4K at 22:03, 22:10, 22:38 and 22:53. Set to `never` on 2026-08-31: `GenerateIntroMarkerBehavior`, `GenerateCreditsMarkerBehavior`, `GenerateAdMarkerBehavior`, `GenerateChapterThumbBehavior`, `LoudnessAnalysisBehavior`, `MusicAnalysisBehavior`; plus `ButlerTaskUpgradeMediaAnalysis=0`. All verified by read-back.
- **Also worth knowing:** Plex's macOS codec bundle ships video **decoders only** (h264, hevc, mpeg2video, mpeg4, vc1) and no software x264 encoder — so video *encoding* on macOS depends entirely on VideoToolbox, with no software fallback. And `FFMPEG_EXTERNAL_LIBS` must end in a trailing slash or `dlopen` fails with "not a file".
- **Containerizing Plex was assessed and deliberately rejected.** It would fix the mount problem outright by using the proven `nas_*` CIFS volumes, but OrbStack's Linux VM on Apple Silicon has no GPU/VideoToolbox passthrough, making it software-transcode-only. Kody's load is 4K and multiple concurrent transcodes, which an M1 cannot serve in software. See `docs/containers/plex.md`. The real long-term answer is a dedicated host with a hardware encoder (Intel QuickSync), which also reclaims RAM/CPU on a 16GB box that currently gives 12GB to OrbStack.
- **Detection improved:** `scripts/mount_health_check.sh` previously caught only `host_mount_shadowed` — the *least* likely of the three ways this mount fails Plex. Added `host_mount_missing` and, more importantly, `host_mount_unresponsive`: a wedged SMB share leaves reads blocking in uninterruptible I/O rather than erroring, so `mount | grep` and `test -d` both report healthy while Plex sits frozen on `stat()`. Detecting that needs a real read under a timeout, implemented in-shell since macOS ships no `timeout(1)`. The healthy path and both new failure paths were tested against real fixtures; the unresponsive path's *timeout mechanism* was verified directly, though not against a genuinely wedged share (can't safely produce one on a live mount).
- **Also noted, not fixed:** Plex's data directory is in **no backup rotation** at all, and now lives on a detachable drive. Watch history, collections, and play state are not regenerable by a rescan.
- **Secret exposure during this work:** a wide `grep -o` with surrounding context printed `PlexOnlineToken` from `Preferences.xml` into the session transcript. Token rotated. Match specific attribute names when reading that file.

### Containers stay dead forever when a NAS CIFS volume fails to mount — the failure mode `restart: always` cannot cover
- **Found:** 2026-08-30, reported by the user as "containers look to be failing to start."
- **What:** At `09:21:56Z` the NAS (`192.168.178.38`) briefly went unreachable. All **9** containers holding a native CIFS volume — `sonarr`, `sonarr-4k`, `radarr`, `radarr-4k`, `unpackerr`, `qbittorrent`, `lazylibrarian`, `audiobookshelf`, `immich-server` — died together with `Exited (255)` at the same instant, and were still dead **2+ hours later** when Kody noticed. Nothing else on the box was affected; the 27 containers without a NAS volume stayed up throughout.
- **Root cause / why nothing self-healed:** a volume mount failure happens at container **creation**, before the entrypoint ever runs. It is not a process exit, so the restart policy is **never consulted** — Docker gives up permanently and the container stays down indefinitely, *even once the NAS is healthy again*. Every one of these 9 services is configured `restart: always` (or `unless-stopped`) and not one of them retried. This is the single most important fact about this failure mode.
- **Why it is invisible:** the error appears **only** in `docker inspect -f '{{.State.Error}}' <container>` — never in `docker logs`. The application logs simply stop mid-stream and look perfectly healthy right up to the cut (Sonarr's last lines were ordinary refresh activity; its "root folder (/mnt/tv) doesn't exist" warnings were a *symptom* of the NAS going away, not a config fault). Diagnosing this from logs alone will mislead you every time.
- **This is a NEW failure mode introduced by the 2026-08-29 CIFS migration**, and a third one distinct from the two in `mount_health_check.sh`. That migration was a genuine improvement, but it moved the mount from a macOS host passthrough (which failed *at runtime*, as `ENOENT`, and so was fixable by a restart loop) to a Docker-managed CIFS mount that fails *at create time* and is therefore immune to restart policy. Retiring the old per-container watch list was correct for the old modes but left this new one uncovered.
- **Fix applied 2026-08-30:** `docker start` on each of the 9 — sufficient and complete, since it re-attempts the CIFS mount, which succeeds the moment the NAS answers. Verified per container that the share was genuinely readable afterwards (real file counts through each mount: 296 TV folders, 522 downloads, 101 movies-4k, 15 tv-4k) rather than trusting an `Up` status.
- **Also found:** `qbittorrent` had been left under the mangled name `fe1a7dd2e49a_qbittorrent`. Watchtower renames a container to `<shortid>_<name>` as step one of an image update; the replacement then failed to be created on this same mount error, leaving the rename half-applied and no container holding the real name. Renamed back with `docker rename` (its config is a host bind mount, so nothing was at risk).
- **Monitoring + auto-remediation added:** `scripts/cifs_volume_health_check.sh` — finds any container in `exited` **or** `created` state whose `.State.Error` is a volume-mount failure, probes each distinct NAS host, and restarts those whose NAS answers. Both states matter: a container that was running when the NAS dropped ends up `exited`, but a fresh one that never came up (Watchtower's replacement, or anything from `compose up`) sits in `created` — filtering on exit status alone silently misses that second case. It deliberately **will not** restart while the NAS is still unreachable (that would only burn failed starts and thrash); it reports `nas_unreachable` and waits. `DRY_RUN=1` detects without touching anything. Safe by construction: `.State.Error` is cleared by Docker on a successful start, so a healthy container can never match.
- **Verified end-to-end**, not just reasoned about: a throwaway container was made to fail on a real NAS subpath, the subpath was then created, and the script was observed healing it (`created` → `running`) while *simultaneously* skipping a second container pointed at a genuinely unreachable host. All test fixtures removed afterwards.
- **Not yet scheduled — needs a decision, see `automation.md`.** Wiring it into workflow 09 is prepared but currently pointless: that workflow's `Mac Mini SSH` credential is broken (see below), so its SSH node cannot run any script at all, and its Discord credential is the literal `"PLACEHOLDER"`, so no alert would be delivered either. A launchd agent (`scripts/com.kody.cifs-volume-healer.plist`, 5-minute interval) is written and tested but **not installed**, pending Kody's go-ahead — it needs no credentials and would work today.
- **Recurred 2026-09-17 — different trigger: the NAS changed IP.** The UNAS came back from an outage on DHCP address `192.168.178.39` instead of `.38`. The same 9 containers failed to mount (`.State.Error` … `operation now in progress`) and stayed down ~4h. The macOS host smbfs mounts (`/Volumes/media`, `/Volumes/downloads`) quietly reconnected to `.39` on their own, which hides the problem: Plex looks fine while every CIFS volume is still hard-wired to `//192.168.178.38/...`. **Diagnose with `arp -an | grep 6c:63:f8:10:1f:a8`** (the UNAS MAC) or `dns-sd -G v4 KP-NAS-01.local` to find where it actually is. **Fix:** Kody pinned the NAS back to `.38`; then `docker start` on the 9 and verified reads through every mount. Repointing to `.39` was rejected — `.38` is also baked into the Docker volume options, Homepage config, the NPM `nas.kodyparton.com` upstream, Uptime Kuma, and several scripts. **Note the healer above would not have fixed this even if installed:** it probes the host from the volume's `device` option, so it would sit on `nas_unreachable` forever while the NAS is healthy at a new address.

### (diagnosis) DNS rebinding protection
- **Symptom:** the Cloudflare A records exist and are correct, NPM is fully configured, yet the hostnames will not resolve on the LAN — only `IP:port` works.
- **This is NOT a missing record.** An earlier diagnosis said the DNS record was absent; that was wrong once the record was added and the symptom persisted. The real cause is one layer lower.

**The proof.** Same hostname, same DNS provider, two transports:

| Query | Result |
|---|---|
| DoH over HTTPS (`cloudflare-dns.com/dns-query`) | ✅ returns `192.168.178.69` |
| Plain DNS on port 53 to the *same* provider (`@1.1.1.1`) | ❌ **times out** |
| Plain DNS for `n8n.kodyparton.com` (answer is a *public* Cloudflare IP) | ✅ answers instantly |

A resolver that genuinely lacked the record would return NXDOMAIN, not time out. Encrypted queries succeed because the network path cannot inspect them. The distinguishing factor is purely **whether the answer contains an RFC1918 private address**.

**Conclusion: something on the network path (UniFi gateway and/or the ISP) is silently dropping DNS responses that contain private IPs — standard DNS rebinding protection.** It is doing its job; the setup just happens to be the exact pattern it defends against (a public DNS name resolving to a LAN address).

### Fixes, best first

**1. UniFi Local DNS Records (recommended for the household).** In UniFi Network → Settings → Routing / DNS → *Local DNS Records*, add `home.kodyparton.com` → `192.168.178.69` and `auth.kodyparton.com` → `192.168.178.69`. The answer then originates **at the gateway**, so it is never a "response in transit" to be filtered. Works for every device on the LAN, including TVs and guests that don't run Tailscale.

**2. Point the Cloudflare records at the Tailscale IP instead.** This Mac is `100.77.239.108`. That is CGNAT space (`100.64.0.0/10`), **not** RFC1918, so rebinding filters ignore it. Verified working: `curl --resolve home.kodyparton.com:443:100.77.239.108 https://home.kodyparton.com/` → **HTTP 200**. Bonus: works from anywhere on the tailnet, not just at home. Cost: every client must be on Tailscale.

**3. Disable rebinding protection on the gateway.** Fixes the root cause but removes a genuine security control — least preferred.

**4. `/etc/hosts` on a single machine.** Immediate, but only that one device. Fine as a stopgap.

Options 1 and 2 combine well: local DNS for devices at home, Tailscale IP for roaming.
